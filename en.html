Face Surgery Simulator

2D 얼굴 이미지에서 코/입/턱 ROI를 시뮬레이션하는 Docker-first 프로젝트입니다.

파이프라인: Upload -> Analyze(3D) -> Modify(ROI) -> Refine(optional AI) -> Export

프론트는 app 이미지에 번들되므로 변경 후 재빌드가 필요합니다.

docker compose -f docker-compose.yml -f docker-compose.ai.override.yml up -d --build app

  1. docker compose -f docker-compose.yml -f docker-compose.ai.override.yml ps

  • model_device == "cuda"
  • face_detector_device == "cuda"
  • three_ddfa_available == true
  • ai_ready == true (quality AI 검증 시 필수)

테스트 실행 전 권장:

  • make preflight-ai-gpu
  • 실패 시 docker compose ... logs app comfyui로 원인 확인 후 재시도

  • FaceBoxes 기본 경로가 CPU로 고정되면 CPU 과점유가 발생할 수 있음
  • OpenCV/BLAS/Torch thread auto 설정 시 CPU 풀코어 점유가 발생할 수 있음
  • 현재 compose 기본값에 thread cap 적용:
    • OMP_NUM_THREADS
    • OPENBLAS_NUM_THREADS
    • MKL_NUM_THREADS
    • NUMEXPR_NUM_THREADS
    • OPENCV_FOR_THREADS_NUM
    • FACE_SIM_TORCH_THREADS

Project Overview

Face surgery simulator using 2D landmark/mesh warping. Supports nose/lip/chin simulation with 3D preview and 2D rendering.

  • Backend: FastAPI + Python 3.9+
  • Frontend: React 18 + TypeScript + Three.js
  • Core CV: MediaPipe, OpenCV, 3DDFA_V2
  • Optional AI refine: ComfyUI

Runtime Preflight Policy

Before tests, verify /api/status:

  • model_device == "cuda" (for GPU tests)
  • three_ddfa_available == true
  • ai_ready == true (for quality + AI validation)

Command:

  • make preflight-ai-gpu

If ai_ready=false, treat quality E2E as blocked and fix runtime first.

UI Behavior Contract

Apply Region is required to trigger /api/modify.

  • Slider changes update local UI state only.
  • Backend modify request is sent only after Apply Region click.
  • If no pending changes exist, Apply remains disabled.

E2E scripts already follow this contract:

  • tests/e2e/test_react_app.py
  • tests/e2e/test_react_case_matrix.py

Code Style Guidelines

Python

  • Import order: stdlib -> third-party -> local
  • Type hints required for public functions
  • Prefer structured error responses over unhandled exceptions
  • Constants: UPPER_CASE, functions/vars: snake_case, classes: PascalCase

TypeScript/React

  • Keep strict typing (avoid any)
  • Component file structure: imports -> types -> helpers -> component
  • API errors should be converted to user-readable messages

Common Pitfalls

  1. Forgetting AI preflight (ai_ready) before quality tests
  2. Running E2E without checking /api/status
  3. Assuming slider movement always emits a deterministic modify request
  4. Treating matrix pass as sufficient without checking Render Signal Warnings in summary.md
  5. Confusing route paths:
    • studio: /studio
    • luxury landing: /luxry/landing
    • luxury viewer: /luxry

Indexed Docs Governance

Last updated: 2026-03-18 Owner: Face Surgery Simulator Team

This file defines repository-wide documentation governance.

1) Objective

  1. Keep a stable, discoverable information architecture.
  2. Make source-of-truth documents explicit.
  3. Ensure code changes and docs changes are updated together.
  4. Prevent root-level documentation sprawl.

2) Naming Rules (Mandatory)

  1. Top-level docs categories use NN_CATEGORY (example: 02_OPERATIONS).
  2. Files inside docs categories use NN_TITLE.md (example: 01_TESTING_PLAYBOOK.md).
  3. Every top-level docs category must include 00_README.md.
  4. Archive folders include a fixed timestamp or date marker.

3) Document Classes

  1. canonical: operational source of truth.
  2. supporting: design/background references.
  3. generated: auto-generated outputs.
  4. archive: frozen historical records.
  5. audience: communication docs tailored to reader level.

4) Scope

Included in governance:

  1. Root key docs: README.md, AGENTS.md, CLAUDE.md, task.md. Agent protocols at docs/01_GOVERNANCE/04_AGENT_PROTOCOLS.md.
  2. docs/**/*.md
  3. docker/*.md, scripts/README.md, reports/README.md
  4. tests/e2e/PLAYWRIGHT.md
  5. Source-adjacent docs such as src/modeling_3d/API_GUIDE.md

Excluded from governance:

  1. Vendored third-party docs (for example models/candidates/**).
  2. Dependency artifacts (node_modules/**).
  3. Temporary local notes and personal workspace files.

5) Source-of-Truth Rules

  1. docs/00_DOCS_HUB.md is the navigation entry point.
  2. docs/01_GOVERNANCE/02_DOCS_INVENTORY.md is the exhaustive docs index.
  3. docs/07_GENERATED/ is the only location for generated docs artifacts.
  4. Archived/frozen references belong under docs/10_ARCHIVE/.
  5. When operational run notes become fragmented, keep one canonical summary in docs/02_OPERATIONS/ and move detailed run logs to docs/10_ARCHIVE/.

6) Code-to-Docs Coupling

When changing these areas, update corresponding docs in the same commit:

  1. API/status behavior (web/backend/main.py) -> docs/03_SPECS/01_API_STATUS_CONTRACT.md
  2. E2E flow and checks (tests/e2e/*) -> docs/02_OPERATIONS/01_TESTING_PLAYBOOK.md, tests/e2e/PLAYWRIGHT.md
  3. Runtime/commands (Makefile, compose files) -> README.md, docs/02_OPERATIONS/02_EXECUTION_PRIORITIES.md, docs/02_OPERATIONS/03_NEXT_ACTIONS.md
  4. Architecture/pipeline (src/modeling_3d/**, src/warp/**) -> docs/04_ARCHITECTURE/*.md, docs/01_GOVERNANCE/03_CODEBASE_MAP.md
  5. Logic validation workflow (scripts/run_logic_validation.py) -> docs/02_OPERATIONS/03_NEXT_ACTIONS.md, docs/02_OPERATIONS/04_RELEASE_GATE_RUNBOOK.md, docs/08_PLANS/*.md

7) Root Cleanup Rules

  1. Do not leave ad-hoc analysis markdown files at repository root.
  2. Do not keep temporary screenshots (for example tmp_*.png) in root.
  3. Personal notes/workspace exports must live outside the repository or under a deliberate archive path in docs/10_ARCHIVE/.
  4. Any file classified as temporary/non-canonical should be removed before merge.

8) Validation and Review

Run documentation validation before commit:

make docs-validate

PowerShell fallback:

py -3 scripts/docs/validate_docs_integrity.py

Review checklist:

  1. No broken local links in docs/.
  2. Inventory includes all markdown docs under docs/.
  3. Numbering rules are respected.
  4. No UTF-8/BOM issues.
  5. Root-level docs remain minimal.

Codebase Map

Last updated: 2026-02-16 Owner: Face Surgery Simulator Team Label: canonical

1) Purpose

This document serves as an easy-to-navigate map for the code structure.

  1. It enables new contributors to locate key files within 10 minutes.
  2. It clarifies which documents need to be updated alongside code changes.
  3. It maintains source of truth connections across tests, operations, and documentation.

In practice, the time spent figuring out "where to look first" often exceeds the time spent on the code itself. This document was written to reduce that initial exploration cost. Especially during incident response or right before a release, quick location identification is critical, so it provides API paths, core modules, test scripts, and documentation reference points linked together in one document.

4) Runtime Processing Flow

The flow below shows how a single request passes through the system internals. When an operational issue occurs, first identifying at which stage of this flow the problem arose greatly reduces root cause analysis time.

ASCII view:

[Browser UI]
    |
    v
[/api/analyze] --> [3D analysis + session creation]
    |
    v
[/api/modify]  --> [ROI transformation] --> [AI correction (optional)] --> [result + quality signals]

flowchart LR
  U["Browser (Studio/Luxury)"] --> A["POST /api/analyze"]
  A --> B["web/backend/main.py"]
  B --> C["Face3DPipeline.analyze()"]
  C --> D["3DDFA/DECA/Fallback provider"]
  D --> E["Session creation (vertices/region_map/history)"]
  E --> F["POST /api/modify"]
  F --> G["3D modify or TPS ROI warp"]
  G --> H["Optional AI refine (ComfyUI/A1111)"]
  H --> I["quality_signals + response image"]
  I --> U

Key contracts:

  1. Analyze creates session state.
  2. Modify updates the session and returns image/mesh.
  3. refine=ai_quality requests may degrade depending on AI readiness state.

In other words, from the user's perspective it is simply "clicking the apply button," but internally it is a multi-stage process where session state management, 3D coordinate transformation, ROI warping, and optional AI correction are performed sequentially.

Quality Metrics Spec

Last updated: 2026-02-15 Owner: Face Surgery Simulator Team Applies to commit: working tree (post PROJECT_IMPROVEMENT_REPORT_2026-02-15)

Purpose

Standardize quality metrics so that under_applied over-classification is reduced and checkpoint/parameter experiment results reflect actual quality differences.

Scope

  • scripts/chin_tuning_experiment.py
  • scripts/checkpoint_benchmark.py
  • scripts/case_matrix_report.py
  • Common implementation: scripts/quality_metrics.py

Input Metrics

  • changed_ratio: Pixel ratio where diff_gray >= low_diff
  • hot_ratio: Pixel ratio where diff_gray >= hot_diff
  • mean_diff: Diff grayscale mean
  • p95_diff: Diff grayscale 95th percentile
  • patch_count: Number of connected components in the hot mask within the specified area range (artifact_patch_min~artifact_patch_max)

Classification Rules

The default label is localized_ok.

  1. under_applied
  • Condition: changed_ratio < min_changed_ratio AND p95_diff < min_p95_signal
  1. global_drift_risk
  • Condition: hot_ratio > max_hot_ratio OR changed_ratio > max_changed_ratio
  1. artifact_risk
  • Condition: patch_count >= artifact_patch_threshold AND hot_ratio >= good_hot_ratio

Score Calculation (quality_score)

  • Range: 0~100
  • Components:
    • signal_score: Based on changed_ratio
    • detail_score: Based on p95_diff
    • locality_score: Based on hot_ratio
    • artifact_score: Based on patch_count

Formula:

quality_score = 100 * (0.45*signal + 0.20*detail + 0.25*locality + 0.10*artifact)

Per-label penalties:

  • under_applied: -12
  • artifact_risk: -8
  • global_drift_risk: -15

Default Thresholds

  • low_diff=8
  • hot_diff=24
  • min_changed_ratio=0.00025
  • target_changed_ratio=0.01000
  • max_changed_ratio=0.12000
  • min_p95_signal=10.0
  • target_p95_signal=30.0
  • good_hot_ratio=0.00800
  • max_hot_ratio=0.04500
  • artifact_patch_min=24
  • artifact_patch_max=1200
  • artifact_patch_threshold=3
  • max_patch_count_for_score=6

Environment Variable Overrides

Common prefix:

  • QUALITY_METRIC_*

Per-script priority prefix:

  • CHIN_TUNE_METRIC_*
  • BENCH_METRIC_*
  • CASE_METRIC_*

Example:

BENCH_METRIC_MIN_CHANGED_RATIO=0.0002
BENCH_METRIC_MAX_HOT_RATIO=0.040

Required Report Items

  • Include classification, reason, quality_score for each case
  • Include quality_score_mean, quality_score_p10 in aggregation
  • Display classification counts and score trends together

AI Pipeline Documentation

This document describes where AI intervenes in this project and under what conditions it falls back.

1) Design Principles

  • Core principle: Geometry First, Local AI Refinement
  • Face shape control is performed through geometric transformation (landmark/mesh)
  • AI only performs local correction around boundaries (seams)

In other words, AI does not regenerate the entire face; instead, it operates as a corrector that naturally blends the ROI transformation results.

2) Processing Flow

  1. 3D/landmark analysis from the input image
  2. ROI (nose/lip/chin) geometric transformation
  3. Seam-band mask generation
  4. ComfyUI inpaint call in Quality mode
  5. Guardrail inspection (locality/drift)
  6. Apply safe fallback (none|poisson|inpaint) on failure

Related code:

  • src/modeling_3d/pipeline.py
  • src/warp/roi_warp.py
  • src/warp/ai_refine.py

3) AI Readiness State Determination

/api/status exposes the following:

  • ai_enabled
  • ai_ready
  • ai_status.checkpoint_count
  • ai_status.checkpoint_resolved
  • ai_status.note
  • face_detector_device (cuda|cpu, actual device of the 3DDFA face detector)
  • runtime_thread_limits (OpenCV/Torch thread cap applied values)

Recent updates:

  • To reduce readiness instability when ComfyUI object_info is slow, the /models/checkpoints path is now queried first.

4) Behavior When Quality Mode Is Requested

When the frontend sends refine=ai_quality:

  1. Backend checks provider readiness
  2. Executes inpaint when ready
  3. Applies guardrail inspection to the result
  4. Demotes to fallback refine if criteria are not met

Related response fields:

  • ai_ready
  • ai_note
  • ai_checkpoint_requested
  • ai_checkpoint_resolved

5) Guardrail Core

src/warp/ai_refine.py key logic:

  • Measure drift outside the mask
  • Measure excessive changes inside the mask
  • Re-localize results around the seam
  • Shape mismatch normalization

Goals:

  • Minimize identity damage outside the ROI
  • Improve boundary naturalness
  • Guarantee safe fallback on failure

6) Operations Checklist

  1. docker compose -f docker-compose.yml -f docker-compose.ai.override.yml up -d --build app comfyui
  2. curl http://localhost:8080/api/status
  3. Verify ai_ready=true
  4. API smoke: scripts/test_api_http.py
  5. E2E: tests/e2e/test_react_app.py (quality + strict)

7) Pipeline Extension Ideas Beyond Boundary Correction (Research-Based)

Below is the order of extensions with highest practical value from the current architecture (3DDFA-based ROI transformation + optional AI refine).

A. Short-term (Immediately applicable, 1-2 weeks)

  1. 3D provider routing (automatic selection based on input state)
  • Idea: Prioritize MICA for frontal/mild expressions, DECA/EMOCA for strong expressions, FaceVerse for Asian detail.
  • Expected benefit: Reduced shape distortion caused by frontal/expression/ethnicity bias.
  1. Expand ROI masks from landmark-only to semantic combination
  • Idea: Get more accurate nose/lip/chin boundaries with BiSeNet/SAM2, composite with soft alpha feather.
  • Expected benefit: Reduced box artifacts around the nose, step artifacts at lip/chin boundaries.
  1. Add shape stabilization regularization
  • Idea: Apply Laplacian smoothing + normal consistency + edge regularization to meshes after modify.
  • Expected benefit: Reduced angularity/distortion of the nose, reduced mesh tearing.
  1. Quality mode identity gate
  • Idea: Require both ArcFace embedding similarity and ROI external change amount (current MAE rule) to pass for confirmation.
  • Expected benefit: Reduced failure cases where "the result no longer resembles the original."

B. Medium-term (High impact, 2-6 weeks)

  1. ControlNet + InstantID/PhotoMaker based local generation
  • Idea: Provide mask/depth/landmark conditions together in quality mode, enforce identity condition.
  • Expected benefit: Improved structural consistency and person identity compared to simple inpaint.
  1. Add local restoration stage
  • Idea: Clean up only the modified area in the final result with CodeFormer/GFPGAN/Real-ESRGAN, then recomposite.
  • Expected benefit: Improved blur/texture breakdown/lip boundary blurring.
  1. Input quality/pose gate + auto frontalize
  • Idea: Frontalize based on yaw/pitch/occlusion score before analyze.
  • Expected benefit: Reduced 3D estimation failure rate from side/semi-side views.

C. Long-term R&D (6 weeks+)

  1. Hybrid renderer (Mesh + 3D Gaussian)
  • Idea: Keep control on parametric mesh, use Gaussian-based rendering for high-quality display.
  • Expected benefit: Alleviate flat skin representation/unnatural lighting in the current 3D viewer.
  1. Drag sculpt UX
  • Idea: In addition to sliders, use point handles (click-drag) to directly specify local deformation vectors.
  • Expected benefit: Enable "intuitive" specification of desired changes from the doctor/consultant perspective.

8) Execution Priority Proposal

  1. Provider routing + semantic ROI + mesh stabilization (first)
  2. Identity gate + quality mode condition strengthening
  3. ControlNet/InstantID integration experiment
  4. Local restoration stage
  5. Hybrid renderer / Drag sculpt R&D

3. Core Technology Detailed Analysis

3.1 Face Detection / Landmark Technology

3.1.1 BlazeFace (Google)

MediaPipe's face detector. A single-shot detector network that outputs rotated 2D bounding rectangles and 5 anchor points from full-resolution RGB input.

  • ~1ms per frame on mobile GPU
  • Based on SSD (Single Shot Detector) architecture
  • After detection, the face landmark model predicts 468 3D landmarks via regression

3.1.2 CNN-based Facial Landmark Detection

The approach used by Zoom and others. A convolutional neural network trained on millions of face data detects 68-120 key points:

  • Jawline contour
  • Lip corners
  • Eyelid margins
  • Brow arches

3.1.3 106-point Landmark (SenseTime / ByteDance / Megvii)

The standard in the Asian app ecosystem. Precisely models face shape with 106 points covering face contour, eyes, nose, mouth, and eyebrows.

3.2 Face Mesh Deformation (Geometric Transformation)

The most fundamental face modification technique with guaranteed real-time performance.

3.2.1 Thin Plate Spline (TPS) Warping

A radial basis function-based non-rigid transformation model introduced by Bookstein (1989):

  • Principle: Smooth interpolation between source landmark set and target landmark set
  • Characteristics: Generates infinitely differentiable smooth surfaces, no manual tuning parameters required, closed-form solution
  • Face Application: Given source/target face landmark sets, one face can be warped to match another face's shape
  • 3D Extension: Used for soft tissue deformation in 3D facial deformation

3.2.2 GPU Sampler-based Face Warping (Intel Patent)

Approach presented in Intel US20180174370A1 / US20170262970A1 patents:

  • Uses GPU's fixed-function sampler engine for warping
  • Backward warping: calculates source coordinates for each pixel then applies bilinear interpolation
  • Combines face shape + facial landmark + skin tone score
  • HD (1280x720) @ 30fps on Intel GPU @400MHz, very low CPU usage
  • Automatic differentiated beautification by gender/age/ethnicity

3.2.3 Facial Reshaping Operator (Hu et al., ESWA 2021)

A well-documented controllable face beautification technique from academia:

  • Captures pairwise geometric configuration with affine-invariant representation
  • Continuous beautification with user-specified weights for individual facial parts
  • Processing within 1 second on a regular laptop
  • Supports both portrait and non-portrait images

3.3 GAN-based Face Editing

3.3.1 FaceApp Approach (Conditional GAN)

  • Generator creates images from noise vectors, Discriminator determines real/fake
  • Conditional GAN: Controls specific attributes by adding condition labels such as age and gender
  • Server-side inference for high-resolution result generation (non-real-time)

3.3.2 StyleGAN-based Face Editing

The most actively researched area recently:

  • Latent space manipulation: Searching for semantic directions in StyleGAN2's W/W+ space
  • Learnable Global Direction (LGD): Learning shared directions for each attribute
  • Instance-Aware Intensity Predictor (IAIP): Fine-tuning global direction based on input instance
  • W++ space: Expanding latent space by replacing FC layers with attention-based transformer
  • PCA/LDA-based feature selection: Enhanced identity preservation
  • StyleMorpheus: Disentangling identity, expression, and appearance for independent control

3.3.3 BeautyGAN (Makeup Transfer)

  • Dual input/output GAN architecture for makeup style transfer
  • Pixel-level histogram loss: Local instance-level loss calculation per facial region
  • Perceptual loss + cycle consistency loss for high quality face generation + identity preservation
  • Uses 3,834 high-resolution face images dataset

3.3.4 Lightweight GAN (Mobile Deployment)

  • BlazeStyleGAN (Google MediaPipe FaceStylizer): 2.01M params, 1.28G FLOPs (256x256 resolution) compared to StyleGAN teacher (33.2M params)
  • Combines knowledge distillation + network pruning + quantization
  • Achieves on-device real-time face stylization on mobile devices

3.4 Diffusion-based Face Editing

A rapidly emerging field in 2024-2025:

3.4.1 InstantID

  • ID-preserving generation from a single face image only
  • Controls facial features in the diffusion process by combining ControlNet + IP-Adapter
  • IdentityNet: Provides strong semantic / weak spatial conditions via facial/landmark image + text prompt
  • Economical and practical with single forward propagation
  • Plug-and-play integration with existing text-to-image models like SD1.5 and SDXL

3.4.2 Identity-preserving Editing with Diffusion

  • Latest research (Springer 2025) simultaneously preserving identity and structure in diffusion-based face editing
  • More diverse editing possible compared to GAN inversion, but inference speed remains a challenge

3.6 Face Parsing / Segmentation

3.6.1 BiSeNet (Bilateral Segmentation Network)

The de facto standard for real-time face parsing:

  • Architecture: Spatial Path (small stride, preserves high-resolution spatial features) + Context Path (fast downsampling, wide receptive field) + Feature Fusion Module
  • Segmentation targets: eyes, nose, mouth, face contour, hair, background, etc.
  • Applications: digital makeup, background removal, skin enhancement, teeth whitening
  • Implementations: Available in both PyTorch and ONNX Runtime inference
  • Performance: Lightweight architecture enabling real-time integration even in video conference apps

3.6.2 Face Parsing Usage in Beautification

  • Per-region differentiated correction: Different processing applied to skin/eye/lip/hair each
  • Mask-based blending: Natural boundary handling between modified and unmodified regions
  • Semantic-based color correction: Color adjustment per semantic region for skin/lips/eyes

4.4 Naturalness Evaluation

Uncanny Valley Problem

  • The state where a face is "almost natural but subtly unnatural" causes the most discomfort
  • Core cause: Mismatch between elements of different photorealism levels (e.g., natural skin + unnatural eyes)
  • Recent research also presents results that an "uncanny slope" (linear increase in likeability with increasing human similarity) is more common

AI-Generated Image Naturalness (AGIN)

  • First systematic study of naturalness for AI-generated images with the AGIN dataset presented in 2024
  • Establishing subjective/objective criteria for naturalness evaluation

Facial Attractiveness Prediction Benchmark

  • LiveBeauty dataset (2024): 10,000 live streaming images + 200,000 attractiveness annotations
  • 7-point Likert scale: Multi-dimensional evaluation including attractiveness, intelligence, trustworthiness, sociability

NeRF/Gaussian-based Arbitrary view synthesis from neural implicit representation Highest quality but high training/inference cost

5.2 Key Developments 2024-2025

  • CVPR 2024 3D Face Reconstruction: 3D reconstruction leveraging geometric guidance from Facial Part Segmentation. Precise shape recovery even in non-frontal poses
  • Edge-based approach: Robust edge-based scheme even with large pose angles or noisy input
  • Challenge: Detail loss in self-occluded areas at large poses remains the core challenge

5.3 Commercial App Strategies

  • ARKit: Maintains tracking via machine learning even for partially occluded faces using IR sensor, immediately recovers full tracking when entire face is visible
  • Banuba SDK: Stable detection at -90 to +90 degree angles. Works at 70% occlusion
  • MediaPipe: Detector determines face location -> landmark model performs 3D surface regression at that location. Detector robustness determines non-frontal capability

6. Identity Preservation Techniques

Making a face "still recognizable as the same person" while modifying it is the core challenge of beautification.

6.1 Identity Preservation in Geometric Transformation

  • Proportional constraint: Limit modification amount proportional to original face size
  • Facial ratio preservation: Maintain key ratios such as inter-eye distance, nose-mouth ratio
  • Affine-invariant operator (Hu et al.): Independent per-part adjustment while preserving geometric configuration

6.2 GAN-based Identity Preservation

Technique Description
Latent to Latent mapper Takes face latent encoding and attribute change as input, encodes identity preservation in training loss
LGD + IAIP Global direction shared per attribute, with per-instance intensity individual adjustment
PCA/LDA feature selection Selectively preserves identity-related features in StyleGAN2 latent space
Disentangled control Separates identity, expression, and appearance for independent control (StyleMorpheus)
Identity-preserving aging (2025) Dedicated methodology for preserving identity during aging/de-aging in StyleGAN latent space

6.3 Diffusion-based Identity Preservation

  • InstantID: IdentityNet combines facial features and landmarks to provide strong semantic condition
  • IP-Adapter-FaceID: Injects Face ID embedding into the diffusion process for identity control
  • Identity and Structure Preserving Editing (Springer 2025): Framework for simultaneously preserving identity and structure in diffusion models

6.4 Loss Function Design

Commonly used losses for identity preservation:

  • Perceptual loss: Distance in VGG/FaceNet feature space
  • Identity loss: Embedding distance from face recognition models like ArcFace
  • Cycle consistency loss: Original reconstruction when reversing the modification
  • Pixel-level histogram loss: Per-region color distribution preservation (BeautyGAN)

7.1 Model Compression Techniques

Technique Description Effect

7.2 Commercial App Optimization Examples

  • MediaPipe Face Mesh: GPU acceleration pipeline applied throughout. 50~1000+ FPS on mobile GPU
  • BlazeFace: ~1ms per frame as single-shot detector (mobile GPU)
  • Intel Face Beautification: HD@30fps + low CPU usage via GPU sampler engine
  • BlazeStyleGAN: On-device face stylization at 256x256 resolution with 1.28G FLOPs

7.3 Pipeline Optimization

  • Two-stage pipeline: Lightweight detector -> precise landmark model (MediaPipe approach)
  • Temporal tracking: Uses previous frame results as initial approximant instead of detection every frame (Banuba approach)
  • Lazy evaluation: Full pipeline execution only when changes are detected
  • GPU-native processing: Minimize CPU-GPU data transfer
