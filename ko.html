파이프라인: Upload -> Analyze(3D) -> Modify(ROI) -> Refine(optional AI) -> Export

docker compose -f docker-compose.yml -f docker-compose.ai.override.yml up -d --build app

    • OMP_NUM_THREADS

AGENTS.md - Face Surgery Simulator

Project Overview

Face surgery simulator using 2D landmark/mesh warping. Supports nose/lip/chin simulation with 3D preview and 2D rendering.

  • Backend: FastAPI + Python 3.9+
  • Frontend: React 18 + TypeScript + Three.js
  • Core CV: MediaPipe, OpenCV, 3DDFA_V2
  • Optional AI refine: ComfyUI

Runtime Preflight Policy

Before tests, verify /api/status:

  • model_device == "cuda" (for GPU tests)
  • three_ddfa_available == true
  • ai_ready == true (for quality + AI validation)

Command:

  • make preflight-ai-gpu

If ai_ready=false, treat quality E2E as blocked and fix runtime first.

UI Behavior Contract

Apply Region is required to trigger /api/modify.

  • Slider changes update local UI state only.
  • Backend modify request is sent only after Apply Region click.
  • If no pending changes exist, Apply remains disabled.

E2E scripts already follow this contract:

  • tests/e2e/test_react_app.py
  • tests/e2e/test_react_case_matrix.py

Code Style Guidelines

Python

  • Import order: stdlib -> third-party -> local
  • Type hints required for public functions
  • Prefer structured error responses over unhandled exceptions
  • Constants: UPPER_CASE, functions/vars: snake_case, classes: PascalCase

TypeScript/React

  • Keep strict typing (avoid any)
  • Component file structure: imports -> types -> helpers -> component
  • API errors should be converted to user-readable messages

Common Pitfalls

  1. Forgetting AI preflight (ai_ready) before quality tests
  2. Running E2E without checking /api/status
  3. Assuming slider movement always emits a deterministic modify request
  4. Treating matrix pass as sufficient without checking Render Signal Warnings in summary.md
  5. Confusing route paths:
    • studio: /studio
    • luxury landing: /luxry/landing
    • luxury viewer: /luxry

Indexed Docs Governance

Last updated: 2026-03-18 Owner: Face Surgery Simulator Team

This file defines repository-wide documentation governance.

1) Objective

  1. Keep a stable, discoverable information architecture.
  2. Make source-of-truth documents explicit.
  3. Ensure code changes and docs changes are updated together.
  4. Prevent root-level documentation sprawl.

2) Naming Rules (Mandatory)

  1. Top-level docs categories use NN_CATEGORY (example: 02_OPERATIONS).
  2. Files inside docs categories use NN_TITLE.md (example: 01_TESTING_PLAYBOOK.md).
  3. Every top-level docs category must include 00_README.md.
  4. Archive folders include a fixed timestamp or date marker.

3) Document Classes

  1. canonical: operational source of truth.
  2. supporting: design/background references.
  3. generated: auto-generated outputs.
  4. archive: frozen historical records.
  5. audience: communication docs tailored to reader level.

4) Scope

Included in governance:

  1. Root key docs: README.md, AGENTS.md, CLAUDE.md, task.md. Agent protocols at docs/01_GOVERNANCE/04_AGENT_PROTOCOLS.md.
  2. docs/**/*.md
  3. docker/*.md, scripts/README.md, reports/README.md
  4. tests/e2e/PLAYWRIGHT.md
  5. Source-adjacent docs such as src/modeling_3d/API_GUIDE.md

Excluded from governance:

  1. Vendored third-party docs (for example models/candidates/**).
  2. Dependency artifacts (node_modules/**).
  3. Temporary local notes and personal workspace files.

5) Source-of-Truth Rules

  1. docs/00_DOCS_HUB.md is the navigation entry point.
  2. docs/01_GOVERNANCE/02_DOCS_INVENTORY.md is the exhaustive docs index.
  3. docs/07_GENERATED/ is the only location for generated docs artifacts.
  4. Archived/frozen references belong under docs/10_ARCHIVE/.
  5. When operational run notes become fragmented, keep one canonical summary in docs/02_OPERATIONS/ and move detailed run logs to docs/10_ARCHIVE/.

6) Code-to-Docs Coupling

When changing these areas, update corresponding docs in the same commit:

  1. API/status behavior (web/backend/main.py) -> docs/03_SPECS/01_API_STATUS_CONTRACT.md
  2. E2E flow and checks (tests/e2e/*) -> docs/02_OPERATIONS/01_TESTING_PLAYBOOK.md, tests/e2e/PLAYWRIGHT.md
  3. Runtime/commands (Makefile, compose files) -> README.md, docs/02_OPERATIONS/02_EXECUTION_PRIORITIES.md, docs/02_OPERATIONS/03_NEXT_ACTIONS.md

Quality Metrics Spec

Last updated: 2026-02-15 Owner: Face Surgery Simulator Team
Applies to commit: working tree (post PROJECT_IMPROVEMENT_REPORT_2026-02-15)

목적

under_applied 과다 판정을 줄이고, 체크포인트/파라미터 실험 결과가 실제 품질 차이를 반영하도록 품질 지표를 표준화합니다.

적용 범위

  • scripts/chin_tuning_experiment.py
  • scripts/checkpoint_benchmark.py
  • scripts/case_matrix_report.py
  • 공통 구현: scripts/quality_metrics.py

입력 지표

  • changed_ratio: diff_gray >= low_diff 픽셀 비율
  • hot_ratio: diff_gray >= hot_diff 픽셀 비율
  • mean_diff: diff grayscale 평균
  • p95_diff: diff grayscale 95 percentile
  • patch_count: hot mask 연결요소 중 지정 면적 구간(artifact_patch_min~artifact_patch_max) 개수

분류 규칙

기본 레이블은 localized_ok 입니다.

  1. under_applied
  • 조건: changed_ratio < min_changed_ratio 그리고 p95_diff < min_p95_signal
  1. global_drift_risk
  • 조건: hot_ratio > max_hot_ratio 또는 changed_ratio > max_changed_ratio
  1. artifact_risk
  • 조건: patch_count >= artifact_patch_threshold 그리고 hot_ratio >= good_hot_ratio

점수 계산 (quality_score)

  • 범위: 0~100
  • 구성:
    • signal_score: changed_ratio 기반
    • detail_score: p95_diff 기반
    • locality_score: hot_ratio 기반
    • artifact_score: patch_count 기반

공식:

quality_score = 100 * (0.45*signal + 0.20*detail + 0.25*locality + 0.10*artifact)

레이블별 패널티:

  • under_applied: -12
  • artifact_risk: -8
  • global_drift_risk: -15

기본 임계치

  • low_diff=8
  • hot_diff=24
  • min_changed_ratio=0.00025
  • target_changed_ratio=0.01000
  • max_changed_ratio=0.12000
  • min_p95_signal=10.0
  • target_p95_signal=30.0
  • good_hot_ratio=0.00800
  • max_hot_ratio=0.04500
  • artifact_patch_min=24
  • artifact_patch_max=1200
  • artifact_patch_threshold=3
  • max_patch_count_for_score=6

환경변수 오버라이드

공통 prefix:

  • QUALITY_METRIC_*

스크립트별 우선 prefix:

  • CHIN_TUNE_METRIC_*
  • BENCH_METRIC_*
  • CASE_METRIC_*

예시:

BENCH_METRIC_MIN_CHANGED_RATIO=0.0002
BENCH_METRIC_MAX_HOT_RATIO=0.040

리포트 반영 의무 항목

  • 각 케이스에 classification, reason, quality_score 포함
  • 집계에 quality_score_mean, quality_score_p10 포함
  • 분류 카운트와 점수 추이를 함께 표기

04_ARCHITECTURE/01_AI_PIPELINE.md

AI Pipeline

Last updated: 2026-03-19

이 문서는 본 프로젝트에서 AI가 어디에 개입하고, 어떤 조건에서 fallback 되는지 정리합니다.

1) 설계 원칙

  • 기본 원칙: Geometry First, Local AI Refinement
  • 얼굴 형태 제어는 기하 변형(landmark/mesh)에서 수행
  • AI는 경계(seam) 주변만 국소 보정

즉, AI가 얼굴 전체를 다시 생성하는 구조가 아니라, ROI 변형 결과를 자연스럽게 연결하는 보정기로 동작합니다.

2) 처리 흐름

  1. 입력 이미지에서 3D/landmark 분석
  2. ROI(코/입술/턱) 기하 변형
  3. seam-band 마스크 생성
  4. Quality 모드일 경우 ComfyUI inpaint 호출
  5. guardrail 검사(지역성/드리프트)
  6. 실패 시 안전 fallback(none|poisson|inpaint) 적용

관련 코드:

  • src/modeling_3d/pipeline.py
  • src/warp/roi_warp.py
  • src/warp/ai_refine.py

3) AI 준비 상태 판정

/api/status는 아래를 노출합니다.

  • ai_enabled
  • ai_ready
  • ai_status.checkpoint_count
  • ai_status.checkpoint_resolved
  • ai_status.note
  • face_detector_device (cuda|cpu, 3DDFA 얼굴 검출기 실제 장치)
  • runtime_thread_limits (OpenCV/Torch thread cap 적용값)

최근 반영:

  • ComfyUI object_info가 느릴 때 readiness가 흔들리던 문제를 줄이기 위해 /models/checkpoints 경로를 우선 조회하도록 보강했습니다.

4) Quality 모드 요청 시 동작

프론트가 refine=ai_quality를 보내면:

  1. 백엔드에서 provider readiness 확인
  2. 준비 완료 시 inpaint 실행
  3. 결과를 guardrail 검사
  4. 기준 미달 시 fallback refine로 강등

관련 응답 필드:

  • ai_ready
  • ai_note
  • ai_checkpoint_requested
  • ai_checkpoint_resolved

5) Guardrail 핵심

src/warp/ai_refine.py 주요 로직:

  • 마스크 외부 드리프트 측정
  • 마스크 내부 과도 변경 측정
  • 결과를 seam 중심으로 재국소화
  • shape mismatch 정규화

목표:

  • ROI 바깥 identity 손상 최소화
  • 경계 자연스러움 개선
  • 실패 시 안전한 fallback 보장

6) 운영 체크리스트

  1. docker compose -f docker-compose.yml -f docker-compose.ai.override.yml up -d --build app comfyui
  2. curl http://localhost:8080/api/status
  3. ai_ready=true 확인
  4. API smoke: scripts/test_api_http.py
  5. E2E: tests/e2e/test_react_app.py (quality + strict)

7) 경계 보정 외 파이프라인 확장 아이디어 (리서치 기반)

아래는 현재 구조(3DDFA 기반 ROI 변형 + 선택적 AI refine)에서 실효성이 높은 확장 순서입니다.

A. 단기(바로 적용 가능, 1~2주)

  1. 3D provider 라우팅 (입력 상태별 자동 선택)
  • 아이디어: 정면/약한 표정은 MICA, 표정 강한 케이스는 DECA/EMOCA, 동양인 디테일은 FaceVerse 우선.
  • 기대효과: 정면/표정/인종 편향으로 생기는 형상 왜곡 감소.
  1. ROI 마스크를 landmark-only에서 semantic 결합으로 확장
  • 아이디어: BiSeNet/SAM2로 코·입술·턱 경계를 더 정확히 얻고, soft alpha feather로 합성.
  • 기대효과: 코 주변 박스 아티팩트, 입술/턱 경계 단차 감소.
  1. 형상 안정화 규제 추가
  • 아이디어: modify 후 메시에 Laplacian smoothing + normal consistency + edge regularization 적용.
  • 기대효과: 코가 각지거나 찌그러지는 현상, 메시 찢김 감소.
  1. Quality 모드 identity gate
  • 아이디어: ArcFace 임베딩 유사도와 ROI 외부 변화량(현재 MAE 규칙)을 동시 통과해야 확정.
  • 기대효과: "닮지 않게 바뀌는" 실패 케이스 감소.

B. 중기(효과 큼, 2~6주)

  1. ControlNet + InstantID/PhotoMaker 기반 국소 생성
  • 아이디어: 품질 모드에서 mask/depth/landmark 조건을 함께 주고, identity 조건을 강제.
  • 기대효과: 단순 inpaint 대비 구조 일관성과 인물 동일성 향상.
  1. 국소 복원 스테이지 추가
  • 아이디어: 최종 결과에서 수정 영역만 CodeFormer/GFPGAN/Real-ESRGAN으로 정리 후 재합성.
  • 기대효과: 블러/텍스처 깨짐/입술 경계 뭉개짐 개선.
  1. 입력 품질/포즈 게이트 + 자동 frontalize
  • 아이디어: yaw/pitch/occlusion 점수 기반으로 정면화 선행 후 analyze.
  • 기대효과: 측면/반측면에서 3D 추정 실패율 감소.

C. 장기 R&D(6주+)

  1. Hybrid renderer (Mesh + 3D Gaussian)
  • 아이디어: 제어는 파라메트릭 메시에 두고, 표시 렌더는 Gaussian 계열로 고품질화.
  • 기대효과: 현재 3D viewer의 평면적 피부 표현/광원 부자연스러움 완화.
  1. Drag sculpt UX
  • 아이디어: 슬라이더 외에 포인트 핸들(클릭-드래그)로 로컬 변형 벡터를 직접 지정.
  • 기대효과: 의사/상담자 입장에서 원하는 변화의 "직관적" 지정 가능.

8) 실행 우선순위 제안

  1. Provider 라우팅 + semantic ROI + mesh 안정화 (가장 먼저)
  2. Identity gate + 품질 모드 조건 강화
  3. ControlNet/InstantID 연동 실험
  4. 국소 복원 스테이지
  5. Hybrid renderer / Drag sculpt R&D

3D Library Evaluation Strategy (2026-03-01)

Last updated: 2026-03-01
Owner: Face Surgery Simulator Team

1) Purpose

Define a benchmark-gated strategy for evolving 3D face modeling providers without breaking naturalness or runtime stability.

2) Current Runtime Baseline

  1. Active web runtime path: web/backend/main.py
  2. Existing references in repository:
    • 3DDFA_V2 candidate integration and reports
    • MediaPipe usage for landmark-related flows
  3. Naturalness/quality evaluation paths:
    • src/evaluation/naturalness_metrics.py
    • tests/e2e/test_react_case_matrix.py
    • scripts/case_matrix_report.py

3) Provider Tiers

Tier A: Production baseline (default)

  1. 3DDFA_V2 + MediaPipe fallback
  2. Why: practical speed/stability for current API and E2E matrix scope.

Tier B: High-detail experimental

  1. DECA (FLAME-based detail representation)
  2. FaceVerse or equivalent detailed 3DMM candidate from existing benchmark flow
  3. Why: evaluate detail gain for quality profile while keeping strict gate checks.

Tier C: Deferred

  1. Providers blocked by missing licensed assets or unstable runtime footprint.
  2. Only re-enter evaluation after dependency/licensing blockers are cleared.

4) Evaluation Metrics

Every provider candidate must report:

  1. Runtime latency (analyze_ms, modify_ms)
  2. Render stability (viewer_panel_nonempty, viewer_canvas_nonempty)
  3. Naturalness outputs (pass/warn/fail, outside_roi_change_ratio, seam_score)
  4. Functional contract reliability (modify_observed, modify_status)

5) Decision Gate

Promote a provider to production only when:

  1. No contract regressions in matrix scope.
  2. No increase in nose-strong fail or unknown grade rate.
  3. Latency remains within profile budget.
  4. Artifact evidence is published in reports/candidate_benchmark/.

6) Integration Constraints

  1. Keep API contract unchanged for frontend.
  2. Preserve fallback path when high-detail provider is unavailable.
  3. Avoid introducing mandatory assets that cannot be shipped in Docker flow.

7) Recommended Next Steps

  1. Keep Tier A as release baseline.
  2. Run Tier B evaluation behind flags and scorecard.
  3. Bind provider decision to the same logic-validation gate used for naturalness.

3. 핵심 기술 상세 분석

3.1 Face Detection / Landmark 기술

3.1.1 BlazeFace (Google)

MediaPipe의 face detector. Single-shot detector network로 full-resolution RGB 입력에서 rotated 2D bounding rectangle과 5개 anchor point를 출력합니다.

  • 모바일 GPU에서 ~1ms per frame
  • SSD (Single Shot Detector) 아키텍처 기반
  • Detection 후 face landmark model이 468개 3D landmark를 regression으로 예측

3.1.2 CNN 기반 Facial Landmark Detection

Zoom 등이 사용하는 방식. Convolutional neural network를 수백만 개의 얼굴 데이터로 학습하여 68~120개 key point를 감지합니다:

  • Jawline contour
  • Lip corners
  • Eyelid margins
  • Brow arches

3.1.3 106-point Landmark (SenseTime / ByteDance / Megvii)

아시아 앱 생태계의 표준. 얼굴 윤곽, 눈, 코, 입, 눈썹을 포함하는 106개 점으로 얼굴 형태를 정밀하게 모델링합니다.

3.2 Face Mesh Deformation (기하 변형)

얼굴 변형의 가장 기본적이고 실시간 성능이 보장되는 기법입니다.

3.2.1 Thin Plate Spline (TPS) Warping

Bookstein(1989)이 도입한 radial basis function 기반 비강체 변환 모델:

  • 원리: 원본 landmark 집합과 목표 landmark 집합 사이의 smooth interpolation
  • 특성: 무한 미분 가능한 smooth surface 생성, 수동 튜닝 파라미터 불필요, closed-form solution
  • 얼굴 적용: source/target 얼굴의 landmark 집합이 주어지면 하나의 얼굴을 다른 얼굴 모양으로 warping 가능
  • 3D 확장: 3D facial deformation에서 soft tissue deformation에 활용

3.2.2 GPU Sampler 기반 Face Warping (Intel 특허)

Intel US20180174370A1 / US20170262970A1 특허가 제시하는 접근:

  • GPU의 fixed-function sampler engine을 활용하여 warping 수행
  • Backward warping: 각 pixel에 대해 source 좌표를 계산 후 bilinear interpolation
  • Face shape + facial landmark + skin tone score를 결합
  • HD (1280x720) @ 30fps on Intel GPU @400MHz, 매우 낮은 CPU 사용률
  • 성별/연령/인종별 차별화된 beautification 자동 적용

3.2.3 Facial Reshaping Operator (Hu et al., ESWA 2021)

학술적으로 잘 정리된 controllable face beautification 기법:

  • Affine-invariant representation으로 pairwise geometric configuration 캡처
  • 개별 facial part에 대해 사용자 지정 가중치로 continuous beautification
  • 일반 노트북에서 1초 이내 처리
  • Portrait / non-portrait 모두 대응

3.3 GAN 기반 얼굴 편집

3.3.1 FaceApp 방식 (Conditional GAN)

  • Generator가 noise vector에서 이미지 생성, Discriminator가 real/fake 판별
  • Conditional GAN: 연령, 성별 등 condition 라벨을 추가하여 특정 속성 제어
  • 서버 사이드 inference로 고해상도 결과 생성 (비실시간)

3.3.2 StyleGAN 기반 Face Editing

최근 가장 활발한 연구 분야:

  • Latent space 조작: StyleGAN2의 W/W+ space에서 semantic direction을 탐색
  • Learnable Global Direction (LGD): 각 attribute에 대한 공유 direction 학습
  • Instance-Aware Intensity Predictor (IAIP): 입력 instance에 따라 global direction을 미세 조정
  • W++ space: FC layer를 attention-based transformer로 대체하여 latent space 확장
  • PCA/LDA 기반 feature selection: identity preservation 강화
  • StyleMorpheus: identity, expression, appearance를 disentangle하여 독립적 제어

3.3.3 BeautyGAN (Makeup Transfer)

  • Dual input/output GAN 구조로 makeup style transfer
  • Pixel-level histogram loss: 얼굴 부위별로 local instance-level loss 계산
  • Perceptual loss + cycle consistency loss로 high quality 얼굴 생성 + identity 보존
  • 3,834장 고해상도 얼굴 dataset 활용

3.3.4 경량 GAN (모바일 배포)

  • BlazeStyleGAN (Google MediaPipe FaceStylizer): StyleGAN teacher (33.2M params) 대비 2.01M params, 1.28G FLOPs (256x256 해상도)
  • Knowledge distillation + network pruning + quantization 결합
  • 모바일 기기에서 on-device 실시간 face stylization 달성

3.4 Diffusion 기반 얼굴 편집

2024-2025년 급격히 부상한 분야:

3.4.1 InstantID

  • 단일 얼굴 이미지만으로 ID-preserving generation
  • ControlNet + IP-Adapter를 결합하여 diffusion process에서 facial feature 제어
  • IdentityNet: facial/landmark image + text prompt로 강한 semantic / 약한 spatial condition 부여
  • 단일 forward propagation으로 경제적이고 실용적
  • SD1.5, SDXL 등 기존 text-to-image 모델과 plug-and-play 통합

3.4.2 Identity-preserving Editing with Diffusion

  • Diffusion 기반 face editing에서 identity와 structure를 동시 보존하는 최신 연구 (Springer 2025)
  • GAN inversion 대비 더 다양한 편집이 가능하나 inference 속도가 과제

3.6 Face Parsing / Segmentation

3.6.1 BiSeNet (Bilateral Segmentation Network)

실시간 face parsing의 사실상 표준:

  • 아키텍처: Spatial Path (작은 stride, 고해상도 spatial feature 보존) + Context Path (빠른 downsampling, 넓은 receptive field) + Feature Fusion Module
  • segmentation 대상: eyes, nose, mouth, face contour, hair, background 등
  • 활용: digital makeup, background removal, skin enhancement, teeth whitening
  • 구현체: PyTorch, ONNX Runtime inference 모두 가용
  • 성능: 경량 아키텍처로 화상회의 앱에서도 실시간 통합 가능

3.6.2 Beautification에서의 Face Parsing 활용

  • 부위별 차별화 보정: skin/eye/lip/hair 각각에 다른 처리 적용
  • mask 기반 blending: 변형 영역과 비변형 영역의 자연스러운 경계 처리
  • semantic 기반 color correction: 피부/입술/눈 등의 색상을 semantic 영역별로 조절

4.4 Naturalness / 자연스러움 평가

Uncanny Valley 문제

  • 얼굴이 "거의 자연스러우나 미세하게 부자연스러운" 상태가 가장 불쾌감을 유발
  • 핵심 원인: 서로 다른 photorealism 수준의 요소 간 mismatch (예: 자연스러운 피부 + 부자연스러운 눈)
  • 최근 연구는 "uncanny slope"(인간 유사도 증가에 따라 호감도 단순 증가)가 더 일반적이라는 결과도 제시

AI-Generated Image Naturalness (AGIN)

  • 2024년 최초로 AI 생성 이미지의 naturalness를 체계적으로 연구하는 AGIN dataset 제시
  • Naturalness 평가를 위한 주관적/객관적 기준 수립

얼굴 매력도 예측 벤치마크

  • LiveBeauty dataset (2024): 라이브 스트리밍 10,000장 + 200,000개 매력도 annotation
  • 7점 Likert 척도: attractiveness, intelligence, trustworthiness, sociability 등 다차원 평가

5.1 접근법 분류

접근법 설명 장/단점
3D 재구성 후 변형 2D 이미지를 3D 모델로 재구성 → 3D 공간에서 변형 → 2D로 재투영 이론적으로 완전하지만 재구성 정밀도에 의존
Pose-aware landmark 비정면 전용 landmark detector 학습 실시간 가능하나 자기 가림(self-occlusion) 영역 처리 어려움
View synthesis 정면화(frontalization) 후 변형 후 원래 view로 복원 정면화 품질이 전체 파이프라인 품질을 결정
NeRF/Gaussian 기반 Neural implicit representation에서 arbitrary view 합성 최고 품질이나 학습/inference 비용이 높음

5.2 2024-2025 주요 발전

  • CVPR 2024 3D Face Reconstruction: Facial Part Segmentation의 geometric guidance를 활용한 3D 재구성. 비정면 포즈에서도 정밀한 형상 복원
  • Edge 기반 접근: 큰 포즈 각도나 noisy input에서도 robust한 edge-based scheme
  • 과제: 큰 포즈에서 self-occluded area의 detail 손실이 여전히 핵심 challenge

5.3 상용 앱의 대응 전략

  • ARKit: IR sensor 기반으로 부분 가려진 얼굴에서도 machine learning으로 추적 유지, 전체 얼굴이 보이면 즉시 full tracking 복구
  • Banuba SDK: -90~+90도 각도에서 안정적 detection. 70% occlusion에서도 동작
  • MediaPipe: Detector가 face location 결정 → landmark model이 해당 location에서 3D surface regression. Detector의 robustness가 비정면 대응력을 결정

6. Identity Preservation 기법

얼굴을 변형하면서도 "같은 사람"으로 인식되게 하는 것이 beautification의 핵심 과제입니다.

6.1 기하 변형에서의 Identity Preservation

  • Proportional constraint: 변형량을 원본 얼굴 크기 비례로 제한
  • Facial ratio 보존: 눈 간 거리, 코-입 비율 등 핵심 비율 유지
  • Affine-invariant operator (Hu et al.): geometric configuration을 보존하면서 부위별 독립 조절

6.2 GAN 기반 Identity Preservation

기법 설명
Latent to Latent mapper Face의 latent encoding과 attribute change를 입력으로 받아, identity 유지를 training loss에 인코딩
LGD + IAIP Global direction은 attribute별로 공유하되, instance별 intensity를 개별 조정
PCA/LDA feature selection StyleGAN2 latent space에서 identity-related feature를 선별적으로 보존
Disentangled control Identity, expression, appearance를 분리하여 각각 독립적 제어 (StyleMorpheus)
Identity-preserving aging (2025) StyleGAN latent space에서 aging/de-aging 시 identity를 보존하는 전용 방법론

6.3 Diffusion 기반 Identity Preservation

  • InstantID: IdentityNet이 facial feature와 landmark를 결합하여 strong semantic condition 부여
  • IP-Adapter-FaceID: Face ID embedding을 diffusion process에 주입하여 identity 제어
  • Identity and Structure Preserving Editing (Springer 2025): Diffusion model에서 identity와 structure를 동시에 보존하는 프레임워크

6.4 Loss Function 설계

identity preservation에 자주 사용되는 loss:

  • Perceptual loss: VGG/FaceNet feature space에서의 거리
  • Identity loss: ArcFace 등 face recognition model의 embedding 거리
  • Cycle consistency loss: 변형 후 역변형 시 원본 복원
  • Pixel-level histogram loss: 부위별 색상 분포 보존 (BeautyGAN)

7. 모바일 최적화 / 경량화 전략

7.1 Model Compression 기법

기법 설명 효과
Quantization FP32 → INT8 등 정밀도 축소 모델 크기 4x 감소, 추론 속도 2-4x 향상
Knowledge Distillation 대형 teacher model의 지식을 소형 student에 전달 BlazeStyleGAN: 33.2M → 2.01M params
Network Pruning 중요도 낮은 weight/channel 제거 구조적/비구조적 pruning으로 FLOPs 감소
Neural Architecture Search 자동으로 효율적 아키텍처 탐색 하드웨어 특화 최적 구조 발견
Efficient Architecture Design MobileNet, ShuffleNet 등 경량 backbone 설계 단계에서부터 모바일 최적화

7.2 상용 앱의 최적화 사례

  • MediaPipe Face Mesh: GPU acceleration pipeline 전체 적용. 모바일 GPU에서 50~1000+ FPS
  • BlazeFace: Single-shot detector로 ~1ms per frame (mobile GPU)
  • Intel Face Beautification: GPU sampler engine 활용으로 HD@30fps + 저 CPU 사용률
  • BlazeStyleGAN: 1.28G FLOPs로 256x256 해상도 on-device face stylization

7.3 파이프라인 최적화

  • Two-stage pipeline: 가벼운 detector → 정밀한 landmark model (MediaPipe 방식)
  • Temporal tracking: 매 프레임 detection 대신 이전 프레임 결과를 initial approximant로 활용 (Banuba 방식)
  • Lazy evaluation: 변화가 감지될 때만 full pipeline 실행
  • GPU-native processing: CPU-GPU 간 데이터 전송 최소화

상용 앱과 학술 연구를 종합하여 naturalness를 달성하는 원칙을 정리합니다.

8.1 변형 수준 제어

원칙 설명 사례

원칙 설명

8.3 Perception 기반 설계

  • Golden ratio: 얼굴 비율의 황금비에 기반한 목표 설정, 그러나 맹목적 적용 회피
  • Gender/age-aware: 성별/연령에 따른 차별화된 보정 (Meitu, Intel 특허)
  • Cultural context: 지역별 미적 기준 차이를 반영한 프리셋 (아시아 앱의 V-line, aegyo-sal 등)
  • Personalization: 개인별 얼굴 특성 분석 후 맞춤형 보정 (Meitu Magical AI)

8.4 Neural Rendering의 이점 (TikTok Bold Glamour 사례)

전통적 AR overlay 대비 neural rendering 방식의 장점:

  • 필터 경계가 보이지 않음 (no visible seam)
  • 머리 움직임에 따른 자연스러운 추적
  • 환경 조명에 적응하는 효과
  • 표정 변화에도 일관된 결과

6. 학술 기법 상세 분석

6.1 TPS (Thin Plate Spline) Warping

Face beautification에서 가장 널리 사용되는 기하 변형 기법. Bookstein(1989) 도입.

  • 커널 함수: U(r) = r^2 * log(r)
  • 장점: Smooth 변형, closed-form solution, 튜닝 불필요
  • GPU 가속: kornia (warp_image_tps), torch-tps → 5-20x 속도 향상

6.2 Face Parsing (BiSeNet / FaRL)

모델 mIoU 속도 특징
BiSeNet (ResNet-18) ~78% 실시간 De facto standard
FaRL (CLIP 기반) ~84% 느림 20M+ face-text pair 사전학습

6.3 StyleGAN / e4e Neural Face Editing

비실시간 고품질 편집. e4e encoder → W+ latent space → attribute direction 이동 → StyleGAN2 generator.

6.4 3D Morphable Model (3DMM) / FLAME

구현체 특징
DECA (SIGGRAPH 2021) FLAME 기반 identity shape
EMOCA (CVPR 2022) 표정 캡처 우수
MICA (ECCV 2022) Metrical accuracy 최고
INFERNO DECA+EMOCA+MICA 통합

6.5 NeRF / 3D Gaussian Splatting (신규)

  • NeRF: 단일 이미지 → novel view synthesis (비실시간)
  • 3D Gaussian Splatting: NeRF 대비 100x 렌더링 속도
  • GaussianAvatars (CVPR 2024): one-shot 3D head avatar, 67 FPS

Documentation Style Playbook

This playbook standardizes high-quality docs for the Face Changer project.

Goals

  • Be scannable in under 60 seconds.
  • Be detailed enough for implementation without follow-up questions.
  • Be consistent across API docs, release notes, runbooks, and reports.

Writing Rules

  1. Use one clear claim per section.
  2. Put decisions and impact before implementation details.
  3. Use examples with real file paths and commands.
  4. Keep terminology stable (studio, luxury, analyze, modify, refine).
  5. Prefer active voice and explicit ownership.

Document Skeleton

Use this order for technical documents:

  1. Purpose
  2. Scope
  3. Architecture/Flow
  4. Operational Steps
  5. Validation
  6. Risks and Rollback
  7. References

Markdown Quality Checklist

  • Headings are concise and ordered correctly.
  • Command snippets are executable as-is.
  • Paths are clickable and repo-relative.
  • Tables use stable columns and no ambiguous labels.
  • Every doc has at least one verification section.

Visual Polish Rules (MD)

  • Keep line length near 80-100 chars for readability.
  • Use short tables for dense comparison.
  • Use callouts sparingly (only for warnings and blockers).
  • Avoid nested bullets; split into additional headings instead.

Release Note Rules

  • Group by user impact, not by internal subsystem only.
  • Translate technical commits into user-facing language.
  • Separate breaking changes from improvements.
  • Keep one line per change item.

API Doc Rules

  • Endpoint first, then auth/session requirements.
  • Add request/response model names even in draft docs.
  • Add failure modes and expected status behavior.
  • Keep examples aligned with current route paths.

Presentation Rules

  • Assertion-evidence format over bullet-heavy slides.
  • One key message per slide.
  • Use strong contrast and consistent visual rhythm.
  • Keep dense details in appendix slides, not in title slides.

Output Standards

  • Canonical docs: docs/
  • Generated artifacts: output/docs_assets/
  • Automation scripts: scripts/docs/
